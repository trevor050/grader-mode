# Phase 2 execution methods

The specification is the final Phase 2 section of `DESIGN.md`. Neither it nor `prompts/` is changed by this implementation. The execution plan records choices made before activation collection.

## Reproduction

Run `uv run modal run -m src.modal_app_2 --run-id phase2-YYYYMMDD` from the repository root. The implementation requires the Phase 1 manifest at `results/raw/phase1-stage2/manifest.json`, whose full ordered 200-problem sample is copied to `results/phase2/manifest.json`. An existing run ID cannot be overwritten. The dedicated app is `grader-mode-phase2`, its results Volume is `grader-mode-phase2-results`, and the shared read/write model cache is `grader-mode-hf-cache`. Phase 1c functions, apps, results, and allocations are not modified.

The GPU image pins PyTorch 2.9.0, Transformers 4.57.3, Accelerate 1.11.0 and NumPy 2.3.4. Qwen3-8B uses the revision in `src/models.py`, BF16 weights, SDPA attention, and the Phase 1 `render_prompt` function with `enable_thinking=False`. The measured initial pilot used Transformers `generate`. The production decoder uses the same HF model forward and `TopPLogitsWarper(0.95)`, logits divided by temperature 0.7, then `torch.multinomial`; top-k is disabled, max_new_tokens is 768, and inputs are left-padded. EOS-finished rows are removed from `DynamicCache` before the next decode step. A runtime greedy parity check against `generate` on unequal-length prompts verifies positions and caching. It computes only the final-position logits. Top-k 0 disables filtering in Transformers. The native tokenizer EOS token stops each row. Native empty thinking prefixes belong to the prompt, not the scored output.

Source references: [Qwen3 model card](https://huggingface.co/Qwen/Qwen3-8B), [Transformers generation API](https://huggingface.co/docs/transformers/v4.57.0/en/main_classes/text_generation).

## Residual stream and controls

Capture runs 400 matched prompts per format (100 development problems, four templates), after the assistant generation prefix. A forward hook on each decoder layer saves only `hidden[:, -1, :]`, using left padding. This is the decoder output before the model's final normalization. The difference of format means is normalized independently per layer. Float64 CPU statistics are computed from float32 copies of the BF16 residual stream. Only directions and statistics are persisted; transient activation arrays are deleted.

Intervention hooks act on each chosen decoder output, every position in prefill and every cached decode step. Ablation computes `x - (x @ d)[..., None] * d`; addition computes `x + alpha*d`. Arithmetic is float32 and the hook returns BF16 residuals. Tuple outputs retain their additional elements. Runtime tensor assertions exercise both hook paths. NumPy tests verify all-position projection removal and the additive projection shift. Five independent Gaussian vectors from NumPy `default_rng(0)` are unit-normalized and saved once, then used in the same hook for all random controls.

Layer numbering is zero-based. Candidate layer centers `(L + 0.5)/depth` must lie in `[0.2, 0.8]`. The first n development problems in selection order, all four templates, form each screen. Lowest screen leak selects three finalists, with lower layer index breaking ties. Each finalist is independently evaluated on all development boxed prompts; lowest full-development leak selects L*. The full-development baseline is shared. Screen rows are not reused in confirmation because full-size batching has different RNG boundaries.

Alpha scale is mean absolute scalar projection of development boxed residuals onto d at L*, equivalent to the mean norm of each projected vector. Multipliers 2, 4, 8, 16 are tested in order on all development no-format prompts. The first increase of at least 0.10 is selected; otherwise multiplier 16 is retained. No degeneration-based reselection is performed. All test interventions use that alpha unchanged.

## Seeds, batching, and budget

Each request retains its Phase 1 request ID and SHA-derived seed. Held-out formats use the same request ID convention with their own format name. The global CPU/CUDA PyTorch RNG is reset before each batch to the first request's Phase 1 seed; Sampling uses one CUDA RNG stream for the batch; removing finished rows changes RNG consumption and later tensor shapes. Requests are ordered by selection rank then template. The raw rows and batch metrics preserve the actual seed and boundaries. Equivalent batches in different interventions start with the same seed. This is batch-level seeding, not independent per-request random streams; results differ from Phase 1's vLLM engine.

Batch capacity uses free GPU memory and worst-case prompt + 768-token KV-cache allocation, with 8 GiB reserved for attention, logits, sampling, and temporary hook tensors. CUDA OOM divides the failing batch and uses each child's first request seed. Successful batches are never replaced. Every batch is flushed and committed to the results Volume.

The first two development baseline batches produce cost projections. After full development baselines, measured seconds/request with a 15% margin determines the plan: reduce screen problems from 25 to 8, 4, then 1 before reducing test templates from four to two. All five random controls and three held-out formats remain. Three full-development confirmations and up to four alpha trials are budgeted. A separate test-launch timing gate can reduce test templates before any test generation or stop the run. The controller checks elapsed time before each batch and within generation, with a shutdown reserve; the execution timeout is derived from remaining budget minus the full 120-second startup allowance and 180-second shutdown reserve, capped at 10,500 seconds. An absolute deadline is passed before spawning so remote checks include provisioning. Local elapsed allocation time, including failed attempts and provisioning, conservatively counts against the $6 L40S cap at $1.95/hour. The accounting excludes concurrent Phase 1c compute; workspace billing is reported separately and may lag.

## Scoring and analysis

The existing `score_response` supplies leak, commit, and correct_commit without modifications. No responses are excluded for degeneration. Whitespace-token four-gram repetition is `(total grams - distinct grams)/total grams`, or zero with fewer than four tokens. Repetition >0.3 is flagged. Numeric overlap is the number of distinct normalized integer values shared with the original problem statement, using Phase 1 `number_values`; overlap <2 is flagged. Empty means `not response.strip()`. Composite degeneration is their logical OR. Strictly more than 10% in a steered cell sets `not_interpretable=true` for that cell and affected contrasts.

Analysis validates exactly 100 test problems and 20 cells per problem/template. Template means, random-direction means, and equal-format means are formed within each problem. Phase 1's `bootstrap_estimate` provides paired whole-problem percentile intervals with 2,000 resamples and seed 0. H9 reports baseline boxed minus ablate d, and mean random ablation minus ablate d. H10 reports add d minus baseline no-format, and add d minus mean random addition. H11 reports baseline minus ablate d separately for each held-out format and equally pooled across all three. The complete analysis is repeated for gold >=10. Development generations do not enter hypothesis estimates. Summaries report counts, rates, intervals, and preregistered degeneration flags without substantive interpretation.

The initial non-compacting pilot stopped after one batch: 128 responses, 768 padded decode steps, 179.336 seconds, mean 388.508 output tokens. Its allocation time remains charged to the Phase 2 cap. These pilot generations do not enter layer/alpha selection or test inference in the subsequent compacting run.
